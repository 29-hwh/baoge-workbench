## 二、阶段一 · 备份功能验证

**做法**：`backup.snapshotToText()` 生成快照 → 解析 → 逐 key 与源存储**严格比对（内容 + 数组顺序）**。

**结果（修复前）**：

| 检查项 | 结果 |
|---|---|
| 快照 app 标识 / version / exportedAt | ✅ 正确（version=1，时间戳存在） |
| counts 与各 key 实际条数一致 | ✅ |
| 8 个 key 快照 data 与源数据逐 key 完全一致 | ✅ books/bookRead/skills/skillAchieved/workouts/body/todos/countdown 全部一致 |
| **🔴 备份范围审计** | **发现缺陷：`templates`（健身·自定义模板，数组型业务数据）不在 `backup.DATA_KEYS`** |
| 🟡 边界审计 | `settings` 为对象型设备偏好，不在快照（设计如此，见异常汇总） |

**结论**：备份链路本身可靠（快照对已覆盖的 8 key 无损、顺序保持），但**覆盖面缺健身模板模块**——若用户收藏过训练模板，备份/换机后这些模板会丢失。

**处置**：修复 `utils/backup.js` —— `DATA_KEYS` 增加 `'templates'`，并注释说明取舍（settings 为设备偏好不入快照）。`pages/profile/profile.js` 的"存储占用统计"与"清空数据"均遍历 `backup.DATA_KEYS`，**一处修改三处受益**（统计与清空自动涵盖模板）。

## 三、阶段二 · 恢复功能验证

**做法**：先生成"恢复基准快照"；随后**模拟灾难现场**——8 个业务 key 全部清空、`todos` 注入 1 条幽灵记录、`workouts` 置空；再 `applySnapshot` 恢复，逐 key 与快照严格比对。

**结果（修复后）**：

| 检查项 | 结果 |
|---|---|
| applySnapshot 返回计数与快照 counts 一致 | ✅ |
| 恢复后 9 个 key 与快照严格一致（含数组顺序） | ✅ 全部一致 |
| 脏数据彻底清除（无幽灵残留） | ✅ 覆盖式恢复正确清场 |
| 各列表内 `_id` 唯一（无 id 冲突/串档） | ✅ |
| settings 边界 | 🟡 保留原值不随恢复覆盖（设备偏好，设计行为） |
| 损坏快照防御 | ✅ `applySnapshot` 校验 app 标识/data 字段，非法内容抛错（profile 层捕获提示） |

**结论**：恢复 = 覆盖式整表还原，正确、幂等；灾难现场（清空 + 混入脏数据）一次恢复即回到与备份完全一致的干净状态。

## 四、阶段三 · 多轮往返压力测试

**做法**：循环执行「① 模拟两轮备份间正常使用（随机增/删/改各模块）→ ② 备份现场 → ③ 脏化全部 key（清空+注入伪条目）→ ④ 恢复 → ⑤ 逐 key 严格比对 + 列表内 id 唯一性」。
**默认 10 轮，另加码 30 轮验证。**

**结果**：

| 轮数 | 结果 |
|---|---|
| 10 轮（默认） | ✅ 每轮恢复后与当轮备份逐 key 一致、id 无冲突，0 丢失 / 0 覆盖 / 0 不一致 |
| 30 轮（加码） | ✅ 同样全绿（正常使用扰动导致条数自然增长，如 todos 5→11、body 3→6，均被完整备份还原） |

**结论**：反复备份-恢复往返不产生数据遗漏、丢失、覆盖或状态不一致；`_id` 全程无冲突；快照-恢复为确定性无损转换。
