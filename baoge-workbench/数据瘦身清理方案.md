# 数据瘦身（清理历史记录）方案

> 解决问题：备份文件超过 5MB 时，导入提示「文件过大，请清理部分历史记录后重新导出」——
> 但原本并没有给出任何清理手段。本方案把这句话变成一条可执行的闭环。

## 一、核心思路：体检 → 试算 → 归档 → 执行

```
① 体检    谁占了多少？        按表统计条数 / 字节 / 占比，降序排列
② 试算    清完能省多少？      dry-run，算出「删几条、省多少」，不落库
③ 归档    删之前先留底        把将被删除的数据复制成归档文件，随时可找回
④ 执行    真正删除            拿到归档成功回执后才删，归档失败即中止
```

**三条铁律**
1. 先看清再动手——所有删除都先给预览数字，不盲删
2. 删之前先留底——清理 ≠ 丢失，被删数据始终有归档可恢复
3. 绝不误删在用的——倒计时 / 训练模板 / 在读书籍不参与自动清理

## 二、关键发现：真正的体积大户是「嵌套打卡流水」

实测一份 291 KB 的数据，**在读书籍占 167 KB（57.5%）**——但它只有 1 条记录。
体积全在 `books.records[]` 这个每天累积的嵌套数组里。

这意味着：**只按「删除 N 天前的记录」清理，根本清不掉最大的那块**。
所以清理方式必须分三类：

| 类别 | 数据表 | 清理方式 | 为什么不能一刀切 |
|---|---|---|---|
| **历史流水** | 待办 / 身体记录 / 训练记录 / 已读书籍 | 按时间删（半年/一年/两年前）、只保留最近 N 条、清空 | 越老越没用，删了不影响当前使用 |
| **内部流水** | 在读书籍 / 在学技能 / 已达成徽章 | **只瘦身内部 `records[]`**（保留最近 30/60 条） | 记录本身代表「进行中」的事，整条删了等于丢书；但内部打卡流水可以截 |
| **受保护** | 倒计时 / 训练模板 | 不参与自动清理，只能手动清空 | 倒计时多为未来事件；模板是用户配置，删了要重新配 |

> 补充：取不到时间字段的记录**一律保留**，宁可多留也不误删。

## 三、四种清理方式（对应不同场景）

| 方式 | 适用 | 操作路径 |
|---|---|---|
| **一键瘦身** | 体积已超标，想一步到位 | 「数据瘦身」→ 点「一键瘦身到 5MB 以下」 |
| **按时间清理** | 想保留最近一段时间 | 点某张表 → 清理半年/一年/两年以前 |
| **按数量保留** | 想固定留多少条 | 点某张表 → 只保留最近 100 条 |
| **内部流水瘦身** | 书籍/技能打卡流水太多 | 点该表 → 打卡流水只留最近 30/60 条 |
| **清空整表** | 某类数据彻底不要了 | 点某张表 → 清空这张表 |

**一键瘦身**的力度是自动算出来的：从「清理半年前」开始逐级加大（180→365→730→1095→1825 天），
取**第一个**能把体积降到目标以下的档位。即「少删、够用」，不做一刀切。
若所有档位都降不到目标，会明确标记 `notEnough` 并提示手动清掉占用最大的表。

## 四、安全机制

- **预览确认**：弹窗显示「将删除 X 条，释放 Y KB」，再让你点确认
- **强制归档**：确认后先把被删数据复制到剪贴板，成功才执行删除；**归档失败则中止，一条都不删**
- **归档可恢复**：归档文件带 `type: cleanup-archive` 标识和找回说明，用「从剪贴板恢复」即可还原
- **危险色确认**：清理按钮用红色 `#A32D2D`，与「清空全部数据」同一视觉语言
- **不动在用数据**：在读书籍本体、倒计时、训练模板永远不会因为「一键瘦身」消失

## 五、代码结构

```
utils/cleanup.js          核心模块（不碰 UI、不做弹窗）
  analyze()               体检：每表条数/字节/占比/时间跨度，按占用降序
  preview(plan)           试算：返回将删条数、释放字节、清理后体积（dry-run）
  buildArchive(plan)      归档：生成只含被删数据的备份文本
  apply(plan)             执行：真正删除，返回每表删除条数
  suggest(targetBytes)    智能推荐：清到目标体积以下的最小力度方案
  describePlan(pv)        把方案翻译成人话
```

`plan` 的四种模式：`{ key, mode: 'before'|'keep'|'all'|'trim', value }`

页面接入：`pages/profile/profile.js` 的 `toggleCleanup` / `suggestClean` / `pickClean` / `_confirmClean`，
UI 在「数据瘦身」卡片。默认收起，点开才做体检，避免每次进页面全量计算。

## 六、验证结果

- `tests/cleanup.test.js`：**53 断言全绿**
- 闭环实测：备份 **7.2 MB → 92.8 KB**（删除 2370 条），瘦身后重新导出的数据**再导入 0 跳过 / 0 修复，往返逐字段一致**，在读书籍本体完好
- 全量回归：261/261 · 11/11 · edge PASS · 容错 50/50 · 梯度 16/16 · 瘦身 53/53

## 七、已知取舍

1. **归档走剪贴板而非文件**：省事（不需要文件系统权限），但归档很大时需要用户手动粘贴到「文件传输助手」保存。
   若后续归档体积普遍偏大，可改走 `wx.shareFileMessage` 直接发文件。
2. **恢复归档会覆盖当前数据**：这是现有恢复机制的行为（恢复语义就是覆盖）。归档文件里已写明这一点。
3. **内部流水保留数固定 30 条**：书籍打卡很密集的用户可能想留更多，已在选项里提供 60 条档位。
